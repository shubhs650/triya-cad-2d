Decisions made in the product interview of 2026-11-01 and during development. Each entry: context → decision → consequences. A decision is changed only by a new entry that supersedes it; never edit history. Threads that believe a decision is wrong open an issue labelled `adr-proposal` and continue with other work.

Format: **DEC-NNN — Title** · *Status* · *Date*

**DEC-035 — The document model is a mutable container of frozen values; `ChangeSet`s carry before/after by reference and block positions; handles only grow** · Accepted · 2026-11-01
Context: ARCHITECTURE.md §4.1 says entities are replaced, never mutated, but does not say where entities live or what a `ChangeSet` holds. Copying immutable maps on every edit is O(n) per command at 100k entities, which breaks T3 (< 16 ms input round trip); a change set without positions cannot restore block entity order (file order is draw order without SORTENTS) on undo. Decision: `DocumentModel` owns mutable maps of frozen entities/records/objects plus an ordered `EntityId[]` per block; it changes only through `apply(changeSet)`, which validates everything (current "before" by reference, free handles, in-range indices) before committing. `ChangeSet` = entities `{added, updated, removed}` with block indices (removal: before the change; addition: after it), keyed `{added, updated, removed}` for each table and for objects, and header `{name, before, after}`; inversion swaps them. `HandleAllocator` starts at `$HANDSEED`, raised past every present handle (including passthrough) if stale, and is monotonic: undo never returns a handle, matching AutoCAD. `EntityIdMap` bindings are permanent for the session. Consequences: undo records are two change sets; render/R-tree caches key on `EntityId` safely; block definitions and layouts are added to `ChangeSet` by the tasks that first edit them (M5 BLOCK, M6 LAYOUT). (M1-01)

**DEC-036 — Geometry tolerance is 1e-10 relative to the drawing's magnitude, floored at 1 unit; full-turn arcs are recognised to rounding** · Accepted · 2026-11-01
Context: ARCHITECTURE.md §4.1 requires an extents-derived epsilon but does not give the rule. A double resolves ~1e-16 relative to the coordinate, so a drawing far from the origin cannot meet an absolute 1e-10, while a fixed relative epsilon on tiny drawings asks for sub-ULP precision. Decision: `toleranceFromExtents(min, max)` gives linear = 1e-10 × max(1, |coordinates|, width, height) and angular = 1e-10 rad; empty extents (AutoCAD's 1e20/−1e20) give the unit tolerance. 1e-10 leaves ~5 digits of headroom over double precision for error accumulated in a few operations and matches AutoCAD's default equal-point tolerance at unit scale. Separately, an ARC or ELLIPSE whose end − start equals 2π to within floating-point rounding of the operands is a full curve (`ccwSweep`), so start + 2π never collapses to a zero sweep. Consequences: kernel functions take a `Tolerance` argument and never hold their own; the M1-02 property tests run at ±1000-unit scale with `toleranceForSize(1000)`. (M1-02)

**DEC-037 — Curve intersections are analytic where a closed form exists and numeric (flatten, seed, Newton) elsewhere; only isolated points are reported** · Accepted · 2026-11-01
Context: M1-02 asks for intersections of all curve pairs, "incl. spline via flattening", but not how exact they must be or what overlap returns; INT/APPINT osnap, TRIM, EXTEND, BREAK and FILLET all build on it. Decision: `intersect(a, b, tol)` splits each curve into linear, circular, elliptic and spline pieces (polylines per segment). Line–line, line–circle/arc, circle–circle and line–ellipse are solved in closed form (the ellipse in its unit-circle frame). Every other pair is flattened, each piece within 1e-3 of its own extent (so a small fillet against a large circle is still sampled finely); chord pairs that cross or come within the sum of both deviations seed Newton's method on the true curves, confined to that chord pair. A pair whose Newton fails, or which might hold a second crossing (the curves turn by more than their crossing angle, the cone test of Bézier clipping), is halved and retried, up to five levels. Results are sorted along `a`, and points closer than `tol.linear` merge. Overlapping stretches (collinear lines, coincident circles or arcs) have no single point to report and return nothing; commands that care about overlap (TRIM, EXTEND, OVERKILL) detect it themselves. Consequences: crossings are exact to `tol.linear`; numeric pairs can miss a crossing only inside a feature smaller than about 1e-3 of a piece's extent that also turns back on itself, which the property tests keep out of their generators (near-cusp splines) and dedicated tests cover. (M1-02)

**DEC-038 — The handle-coverage gate scans each file independently of acad-ts, has no allow-list, and ratchets lost handles by handle** · Accepted · 2026-11-01
Context: M1-27 asks that every handle a corpus file declares be in the reopened document "or on a documented allow-list (folded `VERTEX`/`SEQEND`, free DWG handles)". Measuring it showed neither exception is real: acad-ts keeps vertices, polyface faces, attributes and their `SEQEND` under their file handles inside the owning entity (they are only absent from `getCadObjects()`), and every handle-map entry in the corpus DWGs is a live object record (dynamic-block parameters, solid history, XRECORDs that the reader never reaches). The M0-06 count also skipped binary DXF and DWG types. Decision: (1) the declared list comes from the file alone: the DWG handle map typed from each record header, and ASCII/binary DXF `5` (`105` for `DIMSTYLE`, whose `5` is DIMBLK) outside HEADER and CLASSES; (2) "present" includes objects held by their owner, and there is no other exception, so any future allowance needs its own DEC entry; (3) until M1-31/M1-33 land, `corpus/handle-coverage-baseline.json` lists today's losses per file by handle, and any handle not listed fails, so a new loss cannot hide behind a fixed one. DWG record types are read through acad-ts reader internals (`_readHandles`, `DwgObjectReader._getEntityType`) because acad-ts has no public API for either; the scanner fails loudly if they change.
Consequences: `TESTING.md` §3.2; M1-31 (writer drops) and M1-33 (never loaded) empty the baseline.

**DEC-039 — Entity geometry is the plan view in WCS XY; ±Z extrusions convert exactly, tilted planes stay unmapped** · Accepted · 2026-11-01
Context: `ARCHITECTURE.md` §4.1 left open how M1-04 presents OCS entities and 3D input. Kernel functions (intersections, osnaps, offsets) need every entity in one 2D frame, and the corpus has 314 SOLIDs, 62 TEXTs and 34 MTEXTs with extrusion (0, 0, −1), the usual result of MIRROR in AutoCAD, but no circle or arc on a tilted plane. Decision: `AcadToTriya` gives every entity its plan view in WCS XY. OCS entities with an extrusion along ±Z are converted exactly with AutoCAD's arbitrary-axis algorithm: for −Z, OCS (x, y, z) is WCS (−x, y, −z), so arc angles become π − θ with start and end swapped, ellipse parameters negate and swap, and bulges change sign. WCS entities (LINE, POINT, SPLINE, 3DFACE, 3D POLYLINE, XLINE, RAY) drop Z, which is the exact plan view even when they are not planar. `elevation`, `thickness` and a non-+Z `normal` are carried on the geometry. An OCS entity on a tilted plane, and an XLINE or RAY along Z, has no faithful 2D shape of its kind, so it is reported in `mapEntities(...).unmapped` with its reason and keeps only its retained original (drawn later from proxy data or not at all). Consequences: Triya never edits Z; a save writes an unedited entity from its original (§6.2 rule 2), and an edited one from its plan view at its elevation. VERTEX, SEQEND and ATTRIB entities fold into their POLYLINE or INSERT. Text and blocks (M1-04 part 2): a text frame is its WCS baseline angle with the mirror flags applied in the text's own axes, so a −Z TEXT, ATTDEF or ATTRIB becomes baseline π − θ with upside-down toggled; MTEXT keeps its WCS insertion point and X direction and records `upsideDown` because its Y axis (normal × X) is reversed; an MTEXT that states neither 11 nor 50 runs along the OCS X axis; an INSERT folds −Z into its placement exactly (mirrored position, rotation −θ, scale (−sx, sy, −sz), MINSERT column spacing negated). Annotations (M1-04 part 3): a DIMENSION keeps the DXF reference's frames, so its WCS points 10 and 13–15 drop Z, its OCS points 11, 12 and 16 are mirrored under −Z and its OCS angles 50–53 become π − θ; LEADER vertices are WCS; TOLERANCE converts like MTEXT. A HATCH's boundary edges and pattern lines are OCS: under −Z points mirror, pattern angles become π − θ, and each edge reverses, so `ccw` flips, stored arc angles gain π and ellipse parameters stay (AutoCAD stores a clockwise edge's angles negated). A MULTILEADER's points are all WCS, so they drop Z; it is unmapped when its leader plane (context 111 × 112) is tilted, and its text records `upsideDown` when the text normal is −Z, as MTEXT does. An ACAD_TABLE's insertion point is OCS, as for INSERT, and its horizontal direction (11) WCS, as for MTEXT; its cells carry spans whether the file states them per cell (DXF 175/176, 173) or as merged ranges (DWG). IMAGE and WIPEOUT points and pixel vectors are WCS and drop Z (unmapped when u × v is tilted); a PDFUNDERLAY's insertion point is WCS and its rotation is about its normal, so under −Z it becomes π − θ with `upsideDown`. MLINE points and vectors are WCS and drop Z (unmapped when its normal is tilted). A VIEWPORT is a paper-space frame: its centre drops Z, and the view it shows (target, direction, twist, centre, height) is kept as stated, in model-space terms, with no plan-view conversion. A REGION has no plan-view data of its own in any corpus file (no proxy graphics), so its boundary is read from its ACIS body (`packages/io/src/acis`): points and curves are moved by the body transform (a 3 × 3 matrix applied to row vectors, then translation, then scale; the corpus has only translations, so the matrix order is the ACIS documentation's, untested), and a face whose plane is not ±Z is unmapped. OLE2FRAME corners are WCS and drop Z. An ACAD_PROXY_ENTITY is drawn from its proxy graphics, which are WCS: polylines and polygons drop Z; circles and arcs are kept when their plane is ±Z under the current model transform (read as AcGeMatrix3d rows with the translation in the last column, untested on the corpus), and an arc's plan direction comes from its mapped start vector and normal × start vector, so a mirroring transform reverses it; text, meshes and shells are counted, not drawn. (M1-04)

**DEC-040 — Passthrough-only objects that acad-ts cannot write to DXF from their fields are kept as read and written back raw** · Accepted · 2026-11-01
Context: M1-28 R2/R3 proposed adding `MATERIAL` and `VISUALSTYLE` field writers to the acad-ts DXF writer. The acad-ts DXF reader assigns no `VISUALSTYLE` field at all, so a field writer would have written defaults; the round-trip diff would not notice, because acad-ts would read the same defaults back, but the drawing's visual styles would be gone. Both types are passthrough-only in `FILE_FIDELITY.md`. Decision: with `keepRawDxfPassthroughObjects` (set by `@triya/io`), the DXF reader records the group codes of these objects as read (patch 0021, the M1-30 recorder) and the DXF writer emits them unchanged, rewriting only the handle and owner as for unknown objects. The typed object is still built, and DWG reads and writes are unchanged. An object with no recorded codes (built in memory, or read from DWG and saved to DXF) is still skipped with a notification; since M1-88 (patch 0133) a VISUALSTYLE without codes is written from its fields instead, which the DWG reader fills. Another type joins the list only when its DXF read is lossy and Triya does not edit it.
Consequences: `fidelityDxfReaderConfiguration`; `third_party/acad-ts/PATCHES.md` 0021; a Triya edit to one of these objects would need a field writer first. `ACAD_PROXY_OBJECT` joined in M1-31 part 2 (patch 0063): acad-ts has no DXF field writer for it, and proxies are passthrough-only, because Triya never edits another application's object data. `TABLECONTENT` joined in M1-31 part 4 (patch 0070): it is the payload of the `ACAD_ROUNDTRIP_2008_TABLE_ENTITY` XRECORD in a table's extension dictionary, which only AutoCAD reads, and Triya edits tables through the ACAD_TABLE entity, not through it.

**DEC-041 — `$LASTSAVEDBY` and `$ACADMAINTVER` are allowed round-trip differences: they describe the save, not the drawing** · Accepted · 2026-11-01
Context: after M1-29 parts 1–9 these two variables were the most common difference left in the round-trip suite (144 differences across 74 corpus files). `$LASTSAVEDBY` is the login name of whoever last saved the file, and `$ACADMAINTVER` is the maintenance version of the program that saved it. AutoCAD overwrites both on every save. acad-ts marks both as written by the saving program (`DxfReferenceType.Ignored`): its DXF writer leaves them out, so the reopened file shows the acad-ts defaults, and its DWG writer stamps its own maintenance version. Writing back the original values would claim that the file came from the last user's program, and a browser app has no login name to write instead. Decision: both are allowed to differ after a save, like `$TDUPDATE`. No other header variable changes on these grounds. Consequences: `TESTING.md` §3; `packages/testkit/src/roundtrip/diff.ts`. What Triya itself writes into `$LASTSAVEDBY` is a product choice for the save path (M1-05), not a fidelity rule. (M1-29)

**DEC-042 — Render paths carry quadratic and cubic Béziers** · Accepted · 2026-11-01
Context: the renderer contract (§7.1) packed paths as `M L A E Z`, with only splines flattened. TrueType outlines (M1-41) are quadratic (glyf) or cubic (CFF) Béziers; flattening them at tessellation time would either facet text at deep zoom or multiply the scene cache, and SVG/PDF output wants the curves themselves. Decision: two path commands join the contract, `Q x1 y1 x y` (`PATH_Q` = 5) and `C x1 y1 x2 y2 x y` (`PATH_C` = 6). Canvas 2D draws them natively (`quadraticCurveTo`, `bezierCurveTo`), an affine map carries them exactly by their control points (`transformPath`), and hit testing measures 16 chords of each. Consequences: every path consumer handles them (`canvas2d.ts` drawing and picking, `affine.ts`, the corpus bounds test); a WebGL renderer (DEC-006) must flatten them itself. M1-41 part 2 adds two smaller contract pieces in the same spirit: the primitive colour `'background'` (resolved per frame to the canvas background, for MTEXT masks) and the optional `text: { height, greek }` on text primitives for the 3 px greeking LOD; a renderer must honour both. (M1-41)

**DEC-043 — The ACAD_TABLE table-wide overrides are kept as read on DXF save** · Accepted · 2026-11-01
Context: an ACAD_TABLE in DXF carries its table-wide style overrides (group 93 and the flag words 94–96, then the values they enable, up to the first row height) before its rows. acad-ts models none of them: its DXF reader read them into block reference and cell fields (41 became the X scale), and its DWG writer writes none. M1-31 part 4 gives acad-ts an ACAD_TABLE DXF writer (patch 0068), which needs either a model for these overrides or their codes. Decision: the reader keeps the codes as read on `TableEntity.tableOverrideDxfCodes` (patch 0066), and the DXF writer writes them back in place; a table with none writes 93–96 as 0. The rest of the table (geometry, rows, columns, cells, cell overrides) is written from its fields, so entity edits still apply. Consequences: a Triya edit of table-wide overrides (M4-05) needs fields for them first; a DXF-read table saved to DWG loses them, as before. (M1-31)

**DEC-044 — Bundled fonts are converted Hershey data only; a missing font falls back to its Hershey equivalent before FONTALT** · Accepted · 2026-11-02
Context: DEC-007 and M1-09 planned to bundle Hershey and LibreCAD `.lff` fonts. The LibreCAD font files are GPL v2 or later, not LGPL as `ATTRIBUTION.md` said (issue #32), and a converted font shipped in the app would be a derivative work, which CLAUDE.md forbids. The owner chose Hershey only (2026-11-02). Decision: (1) the bundled fonts are converted from the original Hershey occidental data (`assets/fonts/hershey/hershey.jhf`, the USENET distribution in James Hurt's format, used under its terms: the acknowledgements ship with the data and the fonts are not in NTIS format); ten fonts (`oet-simplex`, `-duplex`, `-complex`, `-triplex`, `-italic`, `-script`, `-scriptc`, `-gothice`, `-gothicg`, `-gothici`) use the ASCII layouts of the Hershey distribution's own mapped fonts; everything past ASCII is ours: Unicode Greek from Hershey's Greek sets where the weight matches, a few Hershey symbols (° ± × ÷ · §), the Latin-1 accented letters built from a Hershey base letter and accent strokes we drew, and a diameter sign for `%%c` (MIT). Nothing comes from LibreCAD. (2) `pnpm fonts:build` writes one Triya stroke-font JSON file per font (`assets/fonts/<name>.json`, half Hershey units, cap height 42), a test fails when they drift from the data, and the app loads each as an SHX font, so measuring and drawing need nothing new. (3) Resolution: the style's own font, else the bundled equivalent of that SHX name (`SHX_EQUIVALENTS`: AutoCAD's Roman, Italic, Script and Gothic fonts descend from Hershey's; TXT and the ISO fonts map to Roman Simplex), else FONTALT (itself through the name map when not loaded), else `oet-simplex`. The named equivalent goes before FONTALT because it stands in for that very font, while FONTALT stands in for any font. Every substitution is recorded (`FontBook.substitutions`) for the health report (M1-25). Consequences: text in a drawing whose fonts are missing draws, with widths that differ from the real fonts; `ATTRIBUTION.md`, `PRD.md` §licensing and `ARCHITECTURE.md` §8 drop LibreCAD; Cyrillic, Latin Extended-A, the Latin-1 letters that are not a base letter plus accent (ß, Æ, Þ, ð), and AutoCAD's ASCII-mapped Greek and symbol fonts are left to M1-59. Supersedes the LibreCAD part of DEC-007. (M1-09, issue #32)

**DEC-045 — Performance targets are measured on generated drawings, not owner-provided bench files** · Accepted · 2026-11-02
Context: PRD §12 measured T2, T3, T5 and T7 on `bench-100k.dwg` and `bench-ga.dwg`, which the owner was to author (M1-26). Until they existed, M1-06 and M1-12 measured on stand-ins and M1-42 waited. The owner decided (2026-11-02) that benchmarks use synthetic data. Decision: `bench-100k` (100k model-space entities, 50 blocks, 5 layouts, 20 layers) and `bench-ga` (25k entities, 30 blocks, 2 layouts, 12 layers) are generated in the test by `packages/testkit/src/bench/drawing.ts` with acad-ts from a seeded PRNG; they are not committed. The entity mix (40 % LINE, 15 % LWPOLYLINE, 10 % each CIRCLE, ARC, INSERT, TEXT, 5 % MTEXT) follows what a drafted GA holds; dimensions and hatches are added when Triya generates their geometry, and a change to the mix or counts needs this entry updated, since it moves every perf number. The PRD's "≈30 MB" and "5 MB" sizes described the expected real files and are dropped: the generated `bench-100k` is 5.2 MB. Consequences: M1-42 done; M1-26 no longer includes bench files; M1-22, M1-44, M2-04 and M10-01 measure on the generated drawings; perf targets keep their numbers.

**DEC-046 — A table states where its rows and columns came from once rows or columns are inserted or deleted** · Accepted · 2026-11-07
Context: a save writes the difference between the model and the file's mapping by handle (M1-05), but an ACAD_TABLE's rows, columns and cells have no handle or other identity in DWG or DXF, and each holds data Triya does not map (tooltips, custom data, content geometry, a DWG's cell style ids, R2010+ row and column cell styles). Comparing grids by place would move that data to the wrong cells after Insert Rows, and matching rows by content is a guess (empty rows are alike). Decision: `TableGeometry` gains `rowOrigins` and `columnOrigins`, each row's (column's) index in the table as the file states it or null for one inserted since, in increasing order; they are absent while the grid is the file's. The table engine's Insert and Delete Rows / Columns (M4-05) keeps them, composing edits against the table as read; the mapper never states them, and the app drops them when a save re-bases the model (M2-13). The save (`export/table-grid.ts`) moves each acad-ts row, column and cell by them and writes each cell against what it was; a grid that changes size without them is refused. Consequences: no row reordering (AutoCAD has no command for it), so origins out of order are refused; M1-75 part 34.

**DEC-047 — Rule 0: Triya is a standalone 2D drafting app; DXF is the save format; AutoCAD compatibility is welcome but not required, and no AutoCAD files are asked of the owner** · Accepted · 2026-11-08
Context: on 2026-11-08 the owner restated the project's purpose: "A standalone separate 2D drafting [app] with functionality similar to AutoCAD. Cross compatibility with AutoCAD is welcomed but not mandatory … spending too much time on [old-version] compatibility is unnecessary. Our primary export will be DXF only, hence focus on it only. We will work on cross compatibility after public launch if it is requested from users … do not ask for any native AutoCAD files for project progress." At that point 69 of 101 M1 tasks were done, and almost every open one waited either on owner-made AutoCAD files (M1-26 reference plots and samples, M0-07 AUDIT) or on DWG and old-version detail (M1-74, M1-101, the DWG branches of M1-75). Decision:
1. **Purpose (Rule 0).** Triya CAD 2D is a standalone 2D drafting application whose commands, input and drawing behaviour follow AutoCAD's, so a drafter's habits carry over. "AutoCAD-like" is about how it works, not about matching AutoCAD's plots pixel for pixel or its files byte for byte.
2. **Save is DXF only**, written as AC1032 (the current DXF version; AutoCAD 2018 to today and other CAD programs read it). DWG save and Save As to older DXF versions are post-launch, on user request. Writer code for them that exists already stays while its tests pass, but gets no new work.
3. **Open** keeps reading DXF (every version) and DWG as it does today, best effort. No new DWG-only or pre-AC1032-only work, except a bug that stops a file opening at all.
4. **The passthrough invariant stays for DXF.** Open → save DXF → reopen must not change what the user did not touch: the round-trip diff stays 0 on the corpus. The existing round-trip and mapping gates on DWG and older versions keep running as regression guards. If keeping one of those green would take DWG-only or old-version-only work, the PR may instead record that file's new difference in the round-trip baseline, naming DEC-047 and the reason. DXF AC1032 files never get that exception.
5. **Rendering is checked against Triya's own reviewed golden images**, not AutoCAD reference plots. M1-24 renders the corpus files headless, commits the output as the reference once it has been looked at in the PR that adds it, and fails later changes that differ beyond tolerance; a deliberate change updates the golden image in the same PR and says why. Rendering rules still follow AutoCAD's documentation and, where that is silent, the common drafter expectation (CLAUDE.md).
6. **No AutoCAD files are asked of the owner**: no reference plots, sample DWGs, AutoCAD AUDIT runs or SHX reference renders. Tasks that waited only on them (M0-07, M1-26, M1-40, M1-61, M1-64, M1-65, M1-71 and the tasks blocked by them) move to the roadmap's post-launch AutoCAD-compatibility list. Where the feature is a v1 requirement, threads author the test drawing themselves: with acad-ts, with ezdxf (MIT) in a script that is committed beside the file, or by hand from the DXF reference.
7. **AutoCAD AUDIT is replaced by an automated DXF check.** PRD G3, §11.4 and T4 now require every Triya-saved corpus DXF to load with ezdxf's `recover` and pass its `audit` with no errors (task M1-103). ezdxf runs in CI only, never in the app.
Consequences: PRD §0 (Rule 0), §3, §4 (non-goals 16–17), FR-F1/F2/F8/F10, FR-A6, FR-Z3, §10–§12, §14; `CLAUDE.md` (Rule 0, stop conditions); `TESTING.md` §1, §2.1, §4, §8; `ARCHITECTURE.md` §6.1 and §16; `FILE_FIDELITY.md` scope note; `ROADMAP.md` M1 exit criteria, M1-20, M1-21, M1-24, M1-37, M1-62, M2-13, M2-16, M5-04, M5-09, M5-10, M8-06, M9-04, M10-02, and the post-launch list. M1-75 takes no new parts after part 39 (#198): a writer that is still missing is added, DXF only, by the M2+ task whose command first creates or edits that object.
